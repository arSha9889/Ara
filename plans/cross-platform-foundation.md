# AraChat — основа для iOS и Desktop без реализации продукта

## 1. Цель документа

Этот документ фиксирует подготовительные архитектурные решения для двух будущих
клиентов AraChat:

- **iOS 17+** — нативный React Native-клиент, развиваемый из существующего
  мобильного проекта;
- **Desktop** — приложение на **Tauri + React** для macOS 14+ и Windows 10+.

Цель — не начать разработку обоих продуктов одновременно и не создавать
заготовки экранов, а уменьшить будущую стоимость входа: не допустить расхождения
API, сессий, уведомлений, realtime-протокола и продуктовых сценариев.

Документ не добавляет Tauri, CocoaPods, зависимости, нативные модули, ключи
подписи, push-провайдеры, экраны или серверные маршруты.

## 2. Наблюдения о текущем репозитории

### 2.1 Мобильный клиент

`apps/android` уже является не Android-only исходным кодом, а React Native
проектом с готовой папкой `ios/`. Основная логика в `src/` написана на
TypeScript и в большинстве случаев потенциально общая для Android и iOS:

- авторизация, обновление и отзыв сессии;
- HTTP-клиент;
- WebSocket-аутентификация, heartbeat и reconnect;
- список и экран личных чатов;
- локализация RU/EN;
- навигация и дизайн-токены.

При этом есть Android-only мост `AppConfig`, от которого зависят:

1. HTTPS-адрес API;
2. язык ОС при первом запуске;
3. генерация случайного `device_id`.

Без равнозначной iOS-реализации этих трёх возможностей приложение не будет
готово к запуску на iOS. Это известная подготовительная задача, а не причина
создавать отдельное iOS-приложение или копировать React Native-код.

### 2.2 Веб и Desktop

Веб-клиент уже реализован на React и является правильной будущей renderer-частью
Desktop-приложения. Для Desktop не следует переписывать интерфейс или заводить
отдельный React-клиент. Tauri позднее должен обернуть существующий веб-интерфейс
и добавить только системные возможности, которых нет у браузера.

### 2.3 Сервер и общие сценарии

FastAPI уже является единственным источником бизнес-правил и HTTP-схем;
WebSocket использует единый способ аутентификации: `connection.authenticate`
первым JSON-сообщением, а не токеном в URL. Это правило сохраняется для iOS и
Desktop.

Модель сессий уже рассчитана на несколько независимых устройств одного
пользователя. Каждый новый клиент должен создавать собственный случайный,
неаппаратный `device_id` и хранить свои refresh-токены отдельно.

## 3. Зафиксированные архитектурные решения

### 3.1 Один продуктовый backend и один набор контрактов

iOS, Android, Web и Desktop обращаются к тем же HTTP- и WebSocket-контрактам.
Клиент не должен получать отдельную бизнес-логику, «мобильные» варианты чатов
или свои правила доступа. Различия допустимы только на уровне платформенной
интеграции: защищённое хранилище, жизненный цикл приложения, push, файловый
выбор, уведомления и системные разрешения.

Изменение API перед выпуском нового клиента должно быть обратно совместимым
либо сопровождаться явным планом одновременного обновления всех поддерживаемых
клиентов. Версионирование URL (`/api/v1`) сейчас специально не вводится: само
по себе оно не делает контракт стабильным и добавит миграцию без пользы.

### 3.2 Общим должен быть контракт, а не весь UI

Нельзя принудительно переиспользовать React DOM-компоненты из `packages/ui` в
React Native: пакет зависит от `react-dom`, а мобильная отрисовка и доступность
у платформ различаются.

Общими должны стать постепенно и только после стабилизации Android:

- API-схемы и типы данных;
- сериализация HTTP- и WebSocket-событий;
- правила валидации и коды ошибок;
- ключи локализации и продуктовая терминология;
- нейтральные дизайн-токены (цвета, типографика, отступы, состояния);
- сценарии сессии, синхронизации и deep link.

Компоненты и навигация остаются платформенными:

- React DOM для Web/Tauri;
- React Native для Android/iOS.

Это защищает от ложной «унификации», при которой общий компонент становится
неудобным и для браузера, и для телефона.

### 3.3 Источник правды для клиентских контрактов

Источник правды — Pydantic-схемы и маршруты FastAPI. Перед началом новой
платформы требуется зафиксировать:

1. опубликованную OpenAPI-спецификацию сборки API;
2. отдельное версионируемое описание WebSocket-событий и их payload;
3. контрактные тесты критичных сценариев: auth/refresh/logout, профиль,
   devices, chats/messages, upload, notifications и calls ICE configuration.

Когда Android API стабилизируется, для TypeScript-клиентов можно генерировать
типы или лёгкий API-клиент из OpenAPI. До этого не нужно создавать третий
вручную поддерживаемый набор DTO в `packages/`: он быстро начнёт расходиться с
сервером и текущими Web/React Native моделями.

### 3.4 Безопасность сессий одинакова, реализация хранилища — платформенная

| Платформа | Место хранения refresh-токена и `device_id` | Правило |
| --- | --- | --- |
| Android | Android Keystore через `react-native-keychain` | Уже реализовано; сохранять модель отдельной сессии на устройство. |
| iOS | iOS Keychain через `react-native-keychain` | Добавить при iOS-вехе; случайный `device_id` генерируется один раз и остаётся в Keychain. |
| Desktop | системное хранилище учётных данных ОС | Не использовать `localStorage` для refresh-токена в установленном приложении. |
| Web/PWA | текущая веб-модель до отдельной security-вехи | Её нельзя механически переносить в Desktop. |

Ни одна платформа не использует аппаратный серийный номер, IMEI, MAC-адрес или
другой постоянный аппаратный идентификатор. `device_id` — случайный opaque ID,
созданный клиентом, нужный только для сессий, PIN и push-токенов.

### 3.5 Уведомление должно описывать цель, а не URL конкретной платформы

Текущая серверная модель уведомления содержит поле `url`, удобное для Web Push.
До запуска iOS и Desktop её нужно расширить обратно совместимым
платформонейтральным назначением, например:

- `kind`;
- `chat_id`;
- `message_id`;
- при необходимости `announcement_id` или иной целевой объект.

Каждый клиент сам преобразует назначение в маршрут своей навигации. Это не
позволит серверу отправить web URL в iOS или Windows-уведомление и сохранит
корректный переход при изменении маршрутов.

Текущий контракт mobile push пока Android-специфичен: provider ограничен
`rustore`/`universal`, а `package_name` — `arachat.messenger`. Перед iOS-вехой
его нельзя просто переиспользовать. Нужен отдельный нейтральный дизайн реестра
push-токенов с явными полями платформы, канала доставки, bundle/package ID и
версии приложения. Выбор APNs-провайдера и реальная доставка откладываются до
подтверждённого физического прототипа.

### 3.6 OAuth и внешние ссылки открываются системно

Если на iOS или Desktop понадобятся Yandex ID/VK ID, авторизация проходит через
системный браузер, а не через встроенный WebView. Возврат в приложение
проектируется через проверенный universal link/deep link, разрешённый сервером
и связанный с исходным `device_id`/OAuth attempt. Access token внешнего
провайдера по-прежнему не попадает в клиент.

## 4. Границы будущих клиентов

### 4.1 iOS

**Подход:** продолжать существующий React Native проект, не создавать
`apps/ios` и не дублировать экранные сценарии.

Первый iOS технический этап должен состоять из малого вертикального среза:

1. iOS-реализация `AppConfig` с настройкой HTTPS API base URL, языком ОС и
   случайным `device_id`;
2. проверка Keychain-хранилища, восстановления refresh-сессии и logout;
3. вход, список чатов, личный чат, WebSocket reconnect;
4. проверка переходов из universal/deep link;
5. только после этого — APNs, вложения, запись голоса, permissions и calls.

Особенности, которые нельзя считать автоматически готовыми от Android:

- разрешения камеры, фото, микрофона и уведомлений;
- поведение в foreground/background и ограничение фонового WebSocket;
- обработка APNs-токена, клика по уведомлению и token rotation;
- аудиосессия, медиа, звонки и screen sharing;
- правила Apple для privacy manifest, usage descriptions, подписей и App Store.

### 4.2 Desktop

**Подход:** добавить Tauri только при старте Desktop-вехи. В `apps/web`
сохраняется единый React renderer; будущая desktop-оболочка отвечает за Rust
часть, сборку, системную интеграцию и безопасные платформенные адаптеры.

Desktop-веха начинается с минимального среза:

1. сборка существующего React UI в Tauri;
2. явная runtime-конфигурация API/WS без привязки к browser host;
3. защищённое хранилище desktop-сессии в credential vault ОС;
4. вход, чаты, realtime, восстановление сессии и logout;
5. локальное уведомление и переход к нейтральному назначению уведомления.

После этого отдельно проверяются файлы, системные диалоги, external links,
автообновление, WebRTC, доступ к микрофону и демонстрация экрана. Эти функции
не следует считать бесплатным результатом работы в браузере: WebView и Windows/
macOS имеют собственные разрешения, подписи и политики распространения.

## 5. Границы слоёв, которые надо соблюдать уже в Android-разработке

Чтобы iOS и Desktop не потребовали переписывания, новые Android-функции должны
сохранять следующие границы:

```text
Feature UI
  -> feature API / presentation state
    -> platform-neutral HTTP, realtime and domain contracts
      -> platform port (secure store, app lifecycle, push, media, links)
        -> Android / iOS / Tauri implementation
```

Практические правила:

1. Не импортировать Android native modules напрямую из экранов или feature API.
   Текущие обращения к `NativeModules.AppConfig` нужно при первой подходящей
   технической вехе закрыть адаптером конфигурации/устройства.
2. `AppState` и системные разрешения не должны проникать в логику чатов,
   авторизации или моделей сообщений.
3. API ошибки должны передаваться через устойчивые серверные коды/типы, а не
   через сопоставление англоязычного текста ошибки в каждом клиенте.
4. Не связывать модели сообщений с элементами UI и не хранить оптимистичные
   client-only поля в серверных DTO.
5. HTTP API, WebSocket и push не должны логировать access token, refresh token,
   пароль, PIN или полный текст личного сообщения.

## 6. План подготовки без реализации продукта

### Фаза A — сейчас: проектные решения

Результат этой фазы — данный документ и следующий список решений, которые
фиксируются в ADR при их принятии:

1. нейтральный формат назначения уведомления;
2. целевые bundle/package IDs и владельцы аккаунтов Apple/Windows/macOS;
3. стратегия distribution: App Store/TestFlight, macOS notarization, Windows
   signing и канал обновлений;
4. политика secure storage для Tauri;
5. transport и обработка callback для OAuth на native/Desktop;
6. критерий выбора следующей платформы после Android.

### Фаза B — во время стабилизации Android: контрактная готовность

Это не отдельный продуктовый клиент. Работы допустимы только как часть
стабилизации уже используемых серверных сценариев:

1. оформить HTTP OpenAPI и WebSocket event contract;
2. добавить контрактные проверки критичных ответов API;
3. устранить Android-only допущения из общих DTO и push-модели;
4. описать матрицу поведения для foreground/background/offline/reconnect;
5. создать таблицу supportability: версия клиента, платформа, минимальная ОС,
   известные ограничения и дата прекращения поддержки.

### Фаза C — выбрать одну следующую платформу, не две

После стабильного Android-релиза выбирается один первый технический spike:

- **iOS первым**, если приоритет — единый нативный мобильный опыт, App Store и
  максимальное переиспользование текущего React Native-кода;
- **Desktop первым**, если приоритет — работа на компьютере, быстрый переход от
  уже развитого Web UI и ранняя проверка desktop WebRTC/screen sharing.

Оба направления не запускаются параллельно до завершения первого базового
среза. Иначе backend-контракты, push и quality assurance будут развиваться на
трёх фронтах и Android потеряет фокус.

### Фаза D — отдельный подготовительный PR перед iOS

Перед первым iOS кодом выполнить отдельный механический рефакторинг
`apps/android` в `apps/mobile`, включая workspace-скрипты, CI и документацию.
Сейчас переименование не выполняется: в Android есть незавершённые изменения и
активный процесс разработки. Нейтральное имя нужно для того, чтобы структура
репозитория честно отражала один React Native-клиент для двух ОС.

## 7. Definition of Ready

### 7.1 Для начала iOS technical spike

- Android auth/chats/realtime baseline стабилен и имеет проходящие тесты;
- Android-зависимый `AppConfig` описан и готова равнозначная iOS-реализация;
- определены iOS bundle ID, минимальная версия iOS 17+, владелец Apple
  Developer account и TestFlight-канал;
- API и WebSocket-контракты проверяются контрактными тестами;
- mobile push-модель перестала быть жёстко привязана к Android package/provider;
- подготовлены реальные устройства минимум для iPhone и iPad-проверки, если
  планшетная поддержка заявляется в продукте.

### 7.2 Для начала Desktop technical spike

- Web UI успешно собирается и его API/WS адреса можно задать вне browser-host;
- определены application ID, владельцы сертификатов и каналы выпуска для macOS
  и Windows;
- выбран и проверен способ хранения секретов в credential vault ОС;
- нейтральное назначение уведомлений заменяет зависимость от web URL;
- подготовлены macOS 14+ и Windows 10+ тестовые среды;
- разрешения, desktop WebRTC, file dialogs, screen sharing и обновления
  признаны отдельными техническими рисками, а не включены в первый срез без
  проверки.

## 8. Что намеренно не делаем сейчас

- не создаём `apps/desktop`, Tauri/Rust конфигурацию или iOS-specific UI;
- не добавляем зависимости «на будущее»;
- не переносим React DOM UI в React Native;
- не запускаем реальный APNs/desktop push;
- не меняем существующие API только ради предположений о будущих платформах;
- не обещаем звонки, screen sharing, offline-first, E2EE или новые виды чатов
  на iOS/Desktop до отдельного подтверждённого дизайна и технического среза.
