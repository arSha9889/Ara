ПЛАН КОМАНДЫ ARACHAT: ДОВЕДЕНИЕ DESKTOP-КЛИЕНТА
Период: 17–31 октября 2026 года
Команда: 8 человек


1. ИСХОДНАЯ ТОЧКА НА 17 ОКТЯБРЯ

Desktop-клиент уже реализован намного шире, чем первый набор экранов входа.
Перед командой не стоит задача заново создавать UI или переносить всё с web
без проверки. Задача на остаток месяца — превратить уже написанный клиент в
проверенный release candidate для закрытой беты.

ПОДТВЕРЖДЕНО В КОДЕ И ЛОКАЛЬНОЙ ПРОВЕРКЕ:

- отдельный Tauri 2 + React-клиент для macOS и Windows;
- production frontend успешно собирается;
- Tauri release-бинарник и ARM64 DMG для macOS успешно собраны;
- целостность локального DMG подтверждена hdiutil verify;
- есть реальный вход и регистрация по e-mail, защищённая сессия через keychain;
- есть личные чаты, медиа, voice/video notes, realtime, уведомления,
  профиль/настройки, E2EE-контур и WebRTC-звонки с демонстрацией экрана;
- есть workflow для macOS DMG и Windows NSIS EXE;
- 3 модульных теста записи медиа проходят.

ЭТО ПОКА НЕ ПОДТВЕРЖДЕНО:

- установка и пользовательские сценарии на Windows 10+;
- сквозная работа всех сценариев с настоящим API, SMTP, WebSocket и TURN;
- камера, микрофон, голосовые/видеозаметки, звонки и демонстрация экрана на
  физических macOS и Windows устройствах;
- подпись Windows, Apple Developer ID и notarization macOS;
- безопасность E2EE после независимой ревизии;
- достаточное автоматическое тестирование: сейчас тестов недостаточно для
  уверенного публичного выпуска.

ГРАНИЦА МЕСЯЦА:

К концу октября команда должна получить закрытый beta release candidate, а не
обещать «весь мессенджер готов». Новые крупные функции добавлять нельзя, пока
не закрыты P0-задачи из этого документа. Группы, каналы, групповые звонки и
новые платформы не входят в текущую работу.


2. ЦЕЛЬ И РЕЗУЛЬТАТ

Цель: проверить существующий Desktop-клиент на macOS и Windows, устранить
критические дефекты и подготовить воспроизводимые пакеты для закрытой беты.

Результат к концу периода:

1) Есть проверенный ARM64 DMG для macOS и NSIS EXE для Windows.
2) На обеих ОС пройдены регистрация, вход, сессия, личный чат, медиа,
   realtime/reconnect и нативные уведомления на реальном API.
3) Звонок и демонстрация экрана либо проверены на физических устройствах,
   либо отключены в beta-сборке и явно отмечены как ограничение.
4) Нет открытых критических и высокоприоритетных дефектов.
5) Есть QA-отчёт, известные ограничения, инструкция бета-тестера и канал
   обратной связи.


3. ПРИОРИТЕТЫ

P0 — БЛОКИРУЕТ ЗАКРЫТУЮ БЕТУ

- сквозной smoke на настоящем API: две учётные записи, регистрация, вход,
  восстановление сессии, logout, direct chat, текст, файл, голос, видеозаметка,
  read receipt, typing, reconnect, уведомление;
- фактическая сборка и установка Windows NSIS, полный базовый тест на Windows;
- тест установки и основного пути на macOS 14+;
- тест camera/microphone/WebRTC/TURN/screen sharing на двух устройствах;
- проверка CORS Tauri для macOS и Windows, отсутствия секретов и корректного
  поведения при истёкшей сессии/недоступной сети;
- определение и настройка строгой CSP вместо текущего "csp": null;
- тестовый план, регресс и фиксация каждого блокера в доске задач;
- решение, какие возможности войдут в beta, а какие будут отключены до
  подтверждения физическими тестами.

P1 — ПОСЛЕ СТАБИЛИЗАЦИИ P0

- вход по AraChat ID и PIN, восстановление пароля, OAuth Yandex/VK;
- выбор и загрузка аватара, телефон и приватность профиля;
- поддержка, жалобы, блокировка пользователей;
- логика пропуска welcome на повторном запуске: флаг hasSeenWelcome уже
  сохраняется, но пока не влияет на стартовый маршрут;
- заметное расширение автотестов для auth, чатов, realtime, E2EE и звонков;
- автообновления, автозапуск, фоновая доставка уведомлений — отдельное решение.

P2 — ПУБЛИЧНЫЙ ВЫПУСК

- сертификат подписи Windows и проверка SmartScreen;
- Apple Developer ID, подпись и notarization DMG;
- независимая security review E2EE и строгая политика ключей;
- публичные release notes и поддержка пользователей после беты.


4. РАСПРЕДЕЛЕНИЕ ЗАДАЧ ПО РОЛЯМ

4.1. Основатель — владелец продукта и релизного решения

- До первого дня утверждает scope закрытой беты: функции P0, отключённые
  возможности и список известных ограничений.
- Даёт решения по продуктовым блокерам максимум за один рабочий день.
- Обеспечивает доступы к staging/production API, SMTP, двум тестовым аккаунтам,
  устройствам macOS/Windows и TURN при проверке звонков.
- На финальной демонстрации принимает go/no-go по данным QA, а не по ощущению.

Результат: согласованная beta-граница и итоговое релизное решение.


4.2. Разработчик 1 (вы) — клиентские сценарии и интеграция API

- Ведёт единый технический бэклог P0, разбивает найденные дефекты на маленькие
  проверяемые задачи и проводит code review.
- Исправляет проблемы в auth, workspace, чатах, медиа, realtime и интерфейсе.
- Совместно с QA воспроизводит и устраняет ошибки на настоящем API, не заменяет
  их локальными заглушками.
- Добавляет тесты к исправлениям, прежде всего для auth, WebSocket-событий и
  состояния чата.
- При необходимости выключает неподтверждённый сценарий beta feature flag или
  честным недоступным состоянием, а не имитацией готовности.

Результат: стабильный пользовательский путь от запуска до личного общения.


4.3. Разработчик 2 — Tauri, безопасность и пакеты

- Собирает macOS и Windows пакеты, поддерживает workflow Desktop packages и
  фиксирует версию каждого артефакта.
- Исправляет дефекты окна, keychain, разрешений камеры/микрофона, native
  notifications, установки и платформенного поведения.
- Проверяет CORS `tauri://localhost` и `http://tauri.localhost` вместе с API.
- Вводит строгую CSP, проверяет package/DMG/логи на секреты и отладочные адреса.
- Готовит план подписи: что нужно для Windows certificate и Apple Developer ID,
  без публикации неподписанного пакета как финального.
- Организует проверку и диагностику WebRTC/TURN, screen share и системного звука
  на целевых платформах.

Результат: воспроизводимые пакеты и закрытые платформенные/security-блокеры.


4.4. Тестировщик 1 — функциональный контур

- Создаёт test cases для auth, сессии, direct chat, текстов, файлов, voice,
  video notes, reactions, replies, edit/delete/pin и read receipts.
- Проверяет негативные сценарии: неверные код/пароль, истёкшая сессия,
  отключённый API, разрыв WebSocket, повторный запуск во время операции.
- Прогоняет два аккаунта на реальном API и описывает дефекты с точными шагами,
  сборкой, ОС, ожидаемым/фактическим результатом и доказательством.
- Выполняет повторную проверку исправлений до закрытия задачи.

Результат: подтверждённый основной сценарий и прозрачный список дефектов.


4.5. Тестировщик 2 — платформы, UX и доступность

- Ведёт матрицу macOS 14+ / Windows 10+, RU/EN, светлая/тёмная тема,
  минимальное окно 960 x 680, масштаб и клавиатурная навигация.
- Проверяет titlebar, установку, первый запуск, native permission prompts,
  reduced motion, читабельность и видимость фокуса.
- На физических устройствах проверяет камеру, микрофон, запись голосовых и
  видеозаметок, входящий/исходящий звонок и screen sharing.
- Отделяет блокирующие UX-ошибки от пожеланий после беты.

Результат: честная таблица совместимости и UX-приёмка beta-сценария.


4.6. Тестировщик 3 — регресс и релизная проверка

- Создаёт компактный smoke-набор и запускает его на каждом candidate-пакете.
- Проверяет чистую установку, первый запуск, удаление и, при наличии старой
  сборки, обновление на macOS/Windows.
- Проверяет артефакты: номер версии, production API, отсутствие тестовых
  учётных записей/секретов, README, известные ограничения и инструкцию.
- После code freeze выполняет полный регресс, формирует QA-отчёт с явным
  перечнем пройденного, непройденного и известных рисков.

Результат: основанный на проверках go/no-go отчёт по release candidate.


4.7. Визионер 1 — продукт и закрытая бета

- Формулирует 3–5 реальных пользовательских историй беты и метрики успеха:
  завершение регистрации, успешное начало диалога, доставка сообщения,
  понятность ошибки.
- Вместе с основателем приоритизирует дефекты: blocker / high / normal / позже.
- Подготавливает состав первых бета-тестеров, сценарий обратной связи и журнал
  продуктовых решений.
- Не ставит задачи разработчикам напрямую: новая идея сначала проходит через
  общий бэклог и оценку P0/P1/P2.

Результат: ограниченная, проверяемая и управляемая закрытая бета.


4.8. Визионер 2 — цельность первого опыта

- Проверяет понятность приветствия, регистрации, разрешений, сетевых ошибок и
  ограничений E2EE/звонков на работающей сборке.
- Согласует RU/EN тексты для ошибок, загрузок, пустых состояний и неподтверждённых
  возможностей, чтобы интерфейс не создавал ложных обещаний.
- Готовит простую инструкцию бета-тестера, скриншоты и форму отправки проблемы.
- Участвует в финальном тесте как новый пользователь, не знакомый с кодом.

Результат: понятная подача продукта и качественный первый опыт беты.


5. ПЛАН НА ОСТАТОК ОКТЯБРЯ

ФАЗА 1 — СТАРТ И ПОДТВЕРЖДЕНИЕ СРЕДЫ (17–21 ОКТЯБРЯ)

- Основатель утверждает beta-scope и выдаёт тестовые доступы/устройства.
- Разработчик 2 формирует macOS/Windows пакеты и проверяет CORS/configuration.
- QA создаёт тест-кейсы и матрицу платформ, затем запускает первый smoke.
- Разработчик 1 вместе с QA устраняет только воспроизводимые P0-дефекты.
- Визионеры фиксируют тестовые истории и тексты ограничений.

Контрольная точка: есть Windows EXE, две тестовые учётные записи, первый
сквозной прогон и список только подтверждённых блокеров.


ФАЗА 2 — СТАБИЛИЗАЦИЯ (22–27 ОКТЯБРЯ)

- Проводятся тесты медиа, realtime, уведомлений, WebRTC/TURN и screen sharing.
- Исправляются блокеры и high-дефекты; к каждому существенному исправлению
  добавляется автоматический или воспроизводимый regression check.
- Проводятся RU/EN, темы, accessibility и сетевые негативные сценарии.
- По итогам проверки неподтверждённые функции либо исправляются, либо честно
  выключаются из beta-границы.

Контрольная точка: RC1 проходит smoke на двух ОС без известных блокеров.


ФАЗА 3 — CODE FREEZE И РЕШЕНИЕ О БЕТЕ (28–31 ОКТЯБРЯ)

- Вносить можно только исправления подтверждённых дефектов и обязательные
  релизные изменения.
- QA выполняет полный регресс и проверку пакетов.
- Разработчики формируют финальные candidate-артефакты и обновляют документацию.
- Визионеры готовят материалы и канал обратной связи.
- Основатель принимает go/no-go на основании QA-отчёта.

Контрольная точка: готовы RC-пакеты, QA-отчёт, известные ограничения, инструкция
для бета-тестера и план следующей итерации.


6. ПРАВИЛА РАБОТЫ

- Каждый день: 15 минут разработчики + QA: сделано / сегодня / блокер.
- Два раза в неделю: triage дефектов с основателем и визионером 1.
- Раз в неделю: демонстрация работающей сборки всей команде.
- Каждая задача имеет владельца, приоритет, критерий приёмки, версию сборки и
  тестовую среду.
- Нельзя закрыть дефект фразой «не повторяется»: QA обязан указать повторную
  проверку и версию, где дефект отсутствует.
- Любая новая крупная функция — P1, пока P0 не закрыт. Она может войти в работу
  только взамен задачи сопоставимого объёма и после явного решения основателя.


7. КРИТЕРИЙ GO ДЛЯ ЗАКРЫТОЙ БЕТЫ

Основатель объявляет GO только когда:

- готовы и проверены установочные пакеты macOS и Windows;
- пройден реальный двухпользовательский smoke на API;
- нет blocker/high дефектов;
- есть результат по звонкам/демонстрации экрана: подтверждено либо выключено;
- QA-отчёт, список ограничений и инструкция бета-тестера опубликованы;
- P0-проверки безопасности, CORS и секретов завершены.

Для публичного релиза дополнительно обязательны Windows code signing и Apple
Developer ID + notarization. Закрытая бета не отменяет эти работы, а только даёт
доказательства, что продукт стоит готовить к ним дальше.
